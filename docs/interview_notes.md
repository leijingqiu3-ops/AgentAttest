# 面试讲解要点

## 1. 这个项目到底解决什么问题？

不是“再做一个 Agent”，而是“给 Agent 做验收”。企业上线 Agent 前真正缺的是：怎么证明它在正常输入下不犯错、在异常输入下不越权、重复跑是否稳定、出错后能不能定位。

## 2. 为什么不用 LLM-as-judge？

因为裁判也会错。2026 年有审计发现某常用 benchmark 的 reward 函数有状态污染，记录成功率 94.3%，回放只有 65.5%；另一项工作发现只有 22.6% 的记录通过能通过四项可信性检查。我的做法是把判定落到状态、工具调用和参数上，LLM 只做证据标注。

## 3. pass@k 和 pass^k 有什么区别？

`pass@k` 是 k 次里至少成功一次，衡量“有没有能力”；`pass^k` 是 k 次全成功，衡量“能不能稳定交付”。上线验收应该看后者，因为生产不给你重试 8 次的机会。

## 4. 你怎么知道用例不是过拟合？

三层：40 条用例里 8 个场景族、每族 5 个变体；`none` 模式测误报，故障模式测漏报；真实 badcase 脱敏后只做种子，公开仓库不放原始内部记录。后续会留 holdout 和人工双标。

## 5. 误报怎么处理？

先看 `none` 模式的失败用例，逐条判断是“用例写错了”还是“Agent 真错了”。我已经遇到过一次：DOC-001 和预置工单重复，Agent 正确地重开了旧单，是我的预期写错了。这个过程本身就是验收的一部分。

## 6. 商业化怎么讲？

两种卖法：

- **上线前验收**：按项目收费，交付验收报告 + 回归集 + trace。
- **上线后回归订阅**：每次模型/提示/工具变更跑一遍，按月收费。

目标客户是已经买了 Agent 但不知道怎么验收的企业，以及做 Agent 交付的系统集成商。壁垒不是框架，是“领域用例 + 判定口径 + 失败归因”。

## 7. 你最大的工程难点是什么？

不是调模型，是让判定可复现：工具调用必须结构化、状态必须可快照、错误必须能回放。以及区分“模型自然犯错”和“我注入的故障”，否则指标会骗人。
