# 简历项目：Agent 验收/审计 Agent

## 一句话

给 LLM Agent 做上线前验收：40 条用例、7 种故障注入、四层确定性断言，输出可回放、可归因的审计报告。

## 技术栈

Python 3.11 / OpenAI 兼容 API（DeepSeek）/ Pydantic / pytest / Markdown + HTML / 结构化 trace / 规则归因 / JSONL 哈希链 + 可选 HMAC-SHA256。

## 我做了什么

- 搭建运行时 Attest 层：工具白名单、必填参数与格式、枚举、RBAC、退课政策、注入启发式；拦截发生在执行前，被拦调用不产生副作用。
- 实现哈希链账本：每次调用记录工具、参数哈希、判定、阻断规则与前后哈希；`verify()` 可重算整条链，篡改一行即失败；支持可选 HMAC。
- 搭建可控靶子 Agent：10 个工具、RBAC、退课政策、工单去重、多轮上下文。
- 设计 40 条用例，覆盖 8 类场景；把 70 条真实平台 badcase 脱敏后导入为候选用例。
- 实现 7 种运行模式：baseline、参数篡改、跳过澄清、上下文丢失、越权、PII 泄露、提前终止。
- 用终态/工具/轨迹/轮次四层确定性断言替代 LLM 裁判；失败归因到 6 类。成本层在单价未校准时降级为 advisory。
- 统计 `pass@1` / `pass^k`、Wilson 95% CI、单任务成本、P95、故障检出率与误报率，输出 MD/HTML + trace JSON。
- 做了一份可交互的验收看板（单文件、离线）：用例 → 7 种跑法 → 断言与工具轨迹逐条对照；并录成 48 秒演示视频。
- 把同一批用例接入 LangGraph ReAct，证明断言、归因、报告与 Agent 框架解耦；两边 `pass^3` 都 100%，差异体现在轮次（3.92 vs 4.50）、token 和延迟上。
- 给 oracle 自己做体检：5 条不变量 + 3 条 known-answer 控制 + 7 类 oracle 缺陷注入；当前 8/8 检查通过、7/7 变异体被抓住。
- 增加完成声明核验：把"已创建工单 / 已退款 / 已重开"与工具调用和终态对照；现有 62 条声明全部有证据，变异体"空口退款"被抓住。
- 增加证据清单：`manifest.json` 记录 summary、verdicts、全部 trace 的 SHA-256；`manifest --verify` 可发现任何改动。

## 结果

**A. 正常模式（不注入，k=3）**

- 120 次运行：`pass@1 = 100%` [96.9, 100.0]，`pass^3 = 100%` [91.2, 100.0]，翻转率 0% [0.0, 8.8]。
- 实际成本 0.98 元 / 120 次（约 0.0082 元/次），P95 9.5 s。
- 这是天花板效应：靶子脚本化、temperature=0，不能外推为真实 Agent 稳定。

**B. 检测器灵敏度（注入变体）**

- 280 次运行：正常模式 40/40 通过，误报 0%。
- `wrong_arg` 25/25、`skip_clarify` 5/5、`context_drop` 10/10、`policy_ignore` 10/10、`pii_leak` 5/5、`early_stop` 36/36（4 条未触发注入，已从分母剔除）。
- 实际成本 1.42 元 / 280 次（约 0.005 元/次），P95 14.0 s。
- LangGraph ReAct 对同一批 40 条用例：`pass^3 = 100%` [91.2, 100.0]，翻转 0%，说明验收器与框架解耦，同时暴露用例饱和。
- 失败分布（93 条，成本校准后）：parameter 25、tool 0、context 15、planning 38、permission 10、data 5。
- 其中 91 条是实际注入并失败的轨迹；另外 2 条是故障不适用场景族的自然失败。91/91 的归因与注入目录预期根因一致（对照注入目录，不是独立人工标注）。
- 成本表校准：估算 6.1142 元 vs 实际 1.42 元，比值 0.232，判定为 miscalibrated；4 条预算误判降级为 advisory，失败总数从 97 修正为 93。

**C. Oracle 自检**

- 1 条 golden trace 全过，8 类 trace 变异体 8/8 被对应断言抓住。

## 简历 bullet（3 条）

- 构建 Agent 验收/审计系统，覆盖 40 条用例、8 类场景、7 种故障注入，以终态/工具/轨迹/预算四层确定性断言替代 LLM 裁判。
- 设计 6 类失败归因（参数/工具/上下文/规划/权限/数据），在 280 次真实 API 运行中实现正常模式 0% 误报；用 8 类 trace 变异体 + 7 类 oracle 缺陷变异体做自检，分别 8/8、7/7 检出。
- 支持 `pass@1` / `pass^3`、Wilson 95% CI、单任务成本与 P95，输出带 trace 证据的审计报告；单次验收约 0.005 元，P95 14 s。

## 面试要能答

- **为什么不用 LLM 裁判**：裁判会漂移；状态和轨迹可回放；LLM 只做证据标注。
- **pass@k 和 pass^k**：前者是至少一次成功，后者是 k 次全成功；上线验收看后者。
- **误报怎么处理**：先跑 `none` baseline，再人工复核；DOC-001 就是一次真实的预期写错。
- **为什么 early_stop 不是 90%**：4 条权限用例没有触发工具调用，注入点没执行；按实际注入 36 条算，是 36/36。
- **oracle 怎么证明不是瞎的**：golden trace + 7 类变异体，必须分别被对应断言抓住。
- **93 和 91 为什么不一样**：91 是实际注入并失败的轨迹；93 是 verdict 失败总数，多出的 2 条是故障不适用场景族的自然失败（CHART-002 / CHART-004）。
- **成本为什么从 97 变成 93**：旧报告把 token 估算当预算判据，4 条 env 用例被误判超预算；现在成本未校准时预算断言只作 advisory。
- **局限**：合成靶子为主、单模型、每族 5 条、区间很宽；κ 只有 30 条样本，CI 0.64–0.96。下一步接更多真实 Agent、扩大标注。
- **商业价值**：运行时拦截 + 上线前验收 + 月度回归；客户是已部署 Agent 的企业和系统集成商。
- **运行时开销**：`engine.check` 约 0.0036 ms/次；账本追加约 0.42 ms/次（本机 2000 次实测），相对 LLM 秒级延迟可忽略。

## 不要夸大

- 不要说“提升 Agent 准确率 X%”——这个项目是验收，不是训练。
- 不要说“生产验证”——目前是可控合成环境。
- 不要说“统计显著”——40 条、每族 5 条，区间很宽；只报区间，不报显著性。
